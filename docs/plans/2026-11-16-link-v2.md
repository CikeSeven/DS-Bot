# 手机连接协议 v2：可恢复的会话，Rust 实现

- 日期：2026-11-16
- 相关：[手机 App](2026-10-24-mobile-app.md)、[手机 API](2026-10-24-mobile-api.md)

## 为什么

v1（`link/src`、`link/server`，TS 和 Dart 各一份）在手机网络上很脆：

- **链路活不过 socket。** 中继每次连接都发一个新的 `connectionId`，而且它被绑进了 Noise prologue。socket 一断，TCP+TLS+WS、hello、connect、Noise 握手、应用层 hello/state/notices 就要全部重来，前后大约 8 个串行往返。断线期间的 `stream`/`message` 事件会丢，正在跑的 RPC 以 `TRANSPORT_CLOSED` 失败，写操作有没有生效也不知道。
- **发现得慢。** 手机端 25–35 s，电脑端 75–90 s，而且电脑端只做了优雅 `close()`，在半开连接上可能一直挂着。
- **一处出错，全部受牵连。** 中继的任何 `error` 帧都会让手机拆掉整个 socket。中继在一侧断开时会立刻删掉链路，所以电脑一抖，所有手机都会掉线。
- **重连策略差。** 固定等 2 s 再重连，没有退避，也不看网络变化。

如果只是换一种语言，这些问题一个都不会消失。所以 v2 改的是协议本身：链路比 socket 活得长，按 seq/ack 重传，断线后用 attach 接回原来的链路。三端共用一份 Rust 实现，手机端通过 flutter_rust_bridge 调用，中继是原生二进制，电脑端用 WASM。这样以后不会再有两份实现慢慢对不上。

## 已定的行为

### 组成

| 部分 | 在哪里 | 做什么 |
|---|---|---|
| 协议核心 | `link/crates/core`（`dsbot-link-core`） | 不含 IO 的状态机：密钥、配对、帧编解码、Noise、可靠通道、`ClientCore`、`HostCore`、`RelayCore`、`DeviceRegistry`、`DeviceStore`。时间全部由调用方传进来（毫秒），动作从 `poll_action()` 取出。 |
| 中继 | `link/crates/relay`（二进制 `dsbot-link-relay`） | tokio + axum 套在 `RelayCore` 外面，用 Docker 部署 |
| 手机端运行时 | `link/crates/client`（`dsbot-link-client`） | tokio + tungstenite + rustls(ring) + webpki-roots 套在 `ClientCore` 外面。同一进程里，同一台电脑只保留一个会话。 |
| 电脑端 | `link/crates/wasm` → `ds-bot/link.wasm` + `ds-bot/link.js` | `HostCore`、`DeviceRegistry`、密钥工具，测试用的 `ClientCore` 和 `RelayCore`，外面套一层很薄的 JS（WebSocket、定时器、RPC 分发） |
| 故障注入测试 | `link/crates/e2e` | 真实中继、电脑端核心和手机端，中间夹一个能断开、能黑洞的 TCP 代理 |

中继的地址路径是 `/v2/link`。v1 的 TS 中继继续跑在 `/v1/link`，等所有设备升级完再停。v2 不和 v1 互通。

### 密钥与身份（与 v1 相同，不需要重新配对）

- **身份密钥**：X25519 密钥对，用不带填充的 base64url 编码。
- **设备 ID**：`deviceId = "d-" + b64url(sha256(pub)[0..16])`。
- **指纹**：`sha256(pub)[0..6]` 转成大写十六进制。
- **随机令牌**：`randomToken(n=32)` 是 n 个随机字节的 b64url。
- **配对链接**：`dsbot://pair?v=1&server=&host=&key=&code=&name=`，格式不变。解析时会检查 `deviceIdFor(key) == host`。
- **握手 hello**：`HandshakeHello` 是 JSON `{name?(≤64 字符), pairingCode?(1..128 字符)}`，空字节解成 `{}`。
- **`DeviceRegistry` 的规则与 v1 完全一样**：
  - 同一时间只有一个配对码，默认 5 分钟过期，输错 5 次作废。
  - 用 `admits` 和 `authorize` 做判断，用 `revoke` 移除设备。
  - 文本比较是常数时间的。
- **中继的设备表**：JSON 格式和 v1 相同，`{deviceId: {role, identityKey, tokenHash, firstSeen, lastSeen}}`，其中 `tokenHash = b64url(sha256(token))`。设备第一次出现时记录下来，之后每次 hello 必须带同一个 token、同一个 role、同一把 key。

### 控制帧（WebSocket 文本帧，JSON）

- **格式**：`{"type": "...", ...字段}`。不认识的字段会被忽略，二进制内容一律用 b64url 编码。
- **大小**：单帧最大 64 KiB。
- **`link`**：链路 ID，16 个随机字节的 b64url。新建链路时由手机生成。

手机或电脑 → 中继：

| type | 字段 | 谁发 |
|---|---|---|
| `hello` | `role:"client"\|"host"`、`deviceId`、`identityKey`、`accessToken`(32–256 字符)、`protocols:[2]`、`fresh?:bool` | 都发，必须是连接后的第一帧 |
| `ping` | `nonce` | 都发 |
| `open` | `link`、`host`(电脑的 deviceId)、`handshake`(Noise msg1) | 手机 |
| `accept` | `link`、`handshake`(Noise msg2) | 电脑 |
| `attach` | `link` | 都发 |
| `close` | `link`、`code` | 都发 |

中继 → 手机或电脑：

| type | 字段 | 说明 |
|---|---|---|
| `hello.ack` | `protocol:2`、`server`、`heartbeatMs`、`graceMs`、`maxFrameBytes` | |
| `pong` | `nonce` | |
| `incoming` | `link`、`client`、`clientKey`、`handshake` | 发给电脑 |
| `opened` | `link`、`handshake` | 发给手机 |
| `attached` | `link`、`peer:"present"\|"away"` | 回给发起 attach 的一方 |
| `peer` | `link`、`state:"away"\|"back"` | 对端的 socket 断了，或者接回来了 |
| `closed` | `link`、`code` | 链路结束 |
| `error` | `code`、`message` | socket 级错误，紧接着关闭 socket（4001；被顶替时是 4003） |

- **`hello` 可以和后面的帧连发**：发完 `hello` 不必等 `hello.ack`，直接发 `open` 或 `attach`。中继按顺序处理，`hello` 失败时，后面的帧全部丢弃。
- **`fresh:true`**：中继关掉这台设备名下的所有旧链路，通知对端 `closed{code:"PEER_RESTARTED"}`。电脑进程每次启动后的第一次 hello 都带这个标记。
- **`closed` 的 code**：
  - `HOST_OFFLINE`：`open` 的时候电脑不在线
  - `REPLACED`：同一对手机和电脑之间开了新链路
  - `EXPIRED`：宽限期到了
  - `LINK_GONE`：`attach` 的链路已经不存在
  - `TIMEOUT`：`open` 后 30 s 内没完成
  - `PEER_RESTARTED`：见上一条
  - `INVALID`：协议违规
  - 对端在 `close` 里写的 code（比如 `NOT_PAIRED`、`DEVICE_REVOKED`、`HOST_BUSY`、`OVERFLOW`、`CLOSED`）原样转发。
- **socket 级的 `error` code**：`AUTH_REQUIRED`、`AUTH_INVALID`、`UNSUPPORTED_VERSION`、`RATE_LIMITED`、`INVALID_MESSAGE`、`SERVER_FULL`、`REPLACED`（同一设备的新 hello 顶掉了旧 socket）。

### 数据帧（WebSocket 二进制帧）

```
0        kind u8      1 = DATA，2 = ACK
1..17    link         16 字节
DATA:  17..25 seq u64 BE（从 1 开始）  25..33 ack u64 BE  33.. ciphertext（至少 16 字节）
ACK:   17..25 ack u64 BE（整帧正好 25 字节）
```

- **中继怎么转发**：只读 `kind` 和 `link`，检查链路存在、已经就绪、发送者是这条链路的一端，然后原样转给另一端。另一端不在时直接丢弃，不做缓存，也不看 seq。
- **`ack` 的含义**：发送方已经按顺序收到的最大 seq，`0` 表示一帧都还没收到。

### 握手

- **Noise 模式**：`Noise_IK_25519_ChaChaPoly_SHA256`，手机是发起方。
- **prologue**：`DS-BOT-LINK\0v=2\0link=<link>\0host=<hostDeviceId>\0client=<clientDeviceId>`（UTF-8）。
- **msg1 和 msg2**：msg1 的负载是手机的 `HandshakeHello`，msg2 的负载是电脑的 `{name?}`。
- **身份校验**：双方都用常数时间比较对方的静态公钥，必须和配对时记下的那把一致。
- **电脑收到 `incoming` 后**：
  1. 检查 `deviceIdFor(clientKey) == client`、链路数是否超过上限（默认 16 条，超了就 `HOST_BUSY`）。
  2. 读 msg1，拿到 hello，询问 `authorize`（可以是异步的）。
  3. 允许就回 `accept`，并把这条链路标记为就绪；不允许就回 `close{NOT_PAIRED}`。
- **建链开销**：只要 1 个端到端往返。手机连发 `hello`、`open`，收到 `opened` 后就能发数据。

### 可靠通道（每条链路、每个方向）

- **加密**：用 snow 的 `StatelessTransportState`，**nonce 就是 seq**。每帧密文最多承载 48 KiB 明文。
- **大消息**：超过 48 KiB 的消息先按 v1 的 `DSBF` 格式分片（17 字节头：`"DSBF"`、版本 `1`、messageId u32、index u16、total u16、totalBytes u32），整条消息最大 4 MiB，同时最多重组 8 条。
- **明文内容**：消息的明文就是 v1 的 `RemoteMessage` JSON（`{"v":1,"id","type","timestamp","payload"}`），类型有 `rpc.request`、`rpc.response`、`rpc.error`、`event`，应用层负载不变。
- **发送**：
  - 按 seq 递增排进队列。窗口是 512 KiB，即已发出但未确认的密文最多 512 KiB，窗口里的帧立即发出，其余排队等待。
  - 只有自己的 socket 已经 attach、并且对端在场时才发。
  - 缓存上限（已发未确认的加上排队的）：电脑端每条链路 8 MiB，手机端 4 MiB。超出就关闭链路，code 是 `OVERFLOW`。
- **接收**：
  - `seq == recv+1`：解密后交付，`recv` 加一。解密失败就关闭链路（`INVALID`）。
  - `seq <= recv`：重复帧，丢弃，并立即回一个 ACK。
  - `seq > recv+1`：跳号，丢弃，并立即回一个 ACK。跳号不致命。
- **确认**：
  - ack 捎带在每个 DATA 帧上。
  - 累计欠 16 帧或 128 KiB 时立即发 ACK 帧，否则 200 ms 后发。
  - 收到的 ack 如果大于自己发出过的最大 seq，就关闭链路（`INVALID`）。
- **重传**：以下三种情况都从 `acked+1` 开始重发（go-back-N，仍受窗口约束），重发的是缓存里原样的密文，帧头里的 ack 改成当前值：
  - 自己 attach 成功
  - 收到 `peer back`
  - 有未确认的数据，而且 RTO 内 ack 一直没前进。RTO 从 3 s 开始，每次翻倍，最大 24 s，ack 一前进就复位。
- **安全性**：
  - ack 和 seq 是明文，没有经过认证。中继伪造 ack 只会造成重传或者链路重置，它本来就能丢帧，所以这不额外影响机密性和完整性。
  - 重放的旧帧满足 `seq <= recv`，会被丢弃。
  - 改动过的密文无法通过认证。

### 断开和恢复

- **一侧 socket 断开**：
  - 中继把这一侧标记为离开，并通知另一侧 `peer{away}`。
  - 链路保留 `graceMs`（`DSBOT_LINK_GRACE_SECONDS`，默认 120 s），到期后删掉，通知还在场的一侧 `closed{EXPIRED}`。
  - 还没就绪的链路直接关闭。
- **断开的一侧回来**：新建 socket，连发 `hello` 和 `attach`。
  - 中继回 `attached{peer}`，如果对端在场，再通知对端 `peer{back}`。
  - 两边各自从 `acked+1` 开始重发，所以不用重新握手，也不用重新同步。
  - 中继在收到同一设备的新 hello 时才发现旧 socket 已经死了，这种情况也一样处理：先通知 `away`，attach 之后再通知 `back`。
- **`attach` 得到 `closed{LINK_GONE}` 或者链路被 `EXPIRED` / `PEER_RESTARTED`**：
  - 手机：未完成的 RPC 以 `SESSION_RESET` 失败，重新 `open`，状态变为 `online{resumed:false}`，应用层再做一次 hello、state、notices。
  - 电脑：丢掉这条链路，取消它上面正在执行的调用。
- **`open` 得到 `HOST_OFFLINE`**：手机保持 socket，按 1、2、4、5 s（上限 5 s）重试 `open`，状态是 `hostAway`。
- **终止状态**：收到 `closed` 且 code 为 `NOT_PAIRED`、`DEVICE_REVOKED`，或者握手时身份不匹配，手机进入 `rejected`，不再自动重连。

### 存活检测和重连

- **中继**：每 15 s 发一个 WS 协议层的 ping，45 s 内收不到任何入站帧（包括 pong）就关闭这个 socket。hello 必须在连接后 5 s 内到达。
- **手机**：
  - socket 静默 10 s 就发一次 `ping`。有调用在等答复、或者有数据还没被确认时，静默 3 s 就发，5 s 内没回应就判定断线。发出后 10 s 内什么都没收到，就**直接丢掉这个 socket，不等它的 close 事件**，并立即重连。
  - 从发 Connect 到收到 `hello.ack` 超过 10 s，按失败处理。
  - `set_foreground(true)` 会立即探测，超时缩短为 5 s。`network_changed()` 会直接丢掉当前 socket 并立即重连。这两种情况都会把退避清零。
- **电脑**：静默 20 s 发 `ping`，10 s 内无回应就直接丢掉这个 socket（不等 close 事件），然后重连。
- **退避**：第一次立即重试，之后是 0.25、0.5、1、2、4、8 s，手机上限 10 s，电脑上限 30 s，都加 ±20% 抖动。收到 `hello.ack` 后复位。

### RPC 和事件

- **手机端的 RPC**：
  - `rpc(method, paramsJson, timeoutMs)`，默认超时 60 s。
  - 链路还没就绪时，请求先排队，就绪后再发。
  - socket 断开不影响正在等待的 RPC，只有会话重置时才以 `SESSION_RESET` 失败。
  - 同一个会话里，每次调用在电脑上恰好执行一次。
- **电脑端的请求处理**：
  - 每条链路同时最多 32 个调用，超出返回 `RATE_LIMITED`。重复的请求 ID 直接忽略。
  - 链路关闭时，正在执行的调用会被取消。
  - `handle(method, params, {deviceId, signal})` 的接口和 v1 一样。
- **事件推送**：`emit(event, data)` 发给所有已就绪的链路，包括暂时离开的那些（事件先缓存，接回后补发）。只要还有已就绪的链路，feed 就一直接着，所以短暂断线期间的事件不会丢。

### 手机端状态（交给 Dart）

| 状态 | 什么时候 |
|---|---|
| `connecting` | 还没建立过链路 |
| `online{resumed}` | 链路就绪。`resumed:false` 表示经过了新的握手，需要全量同步；`resumed:true` 表示原链路接回，什么都不用做 |
| `reconnecting{attempt, error}` | socket 断了，链路还保留着 |
| `hostAway` | socket 正常，但电脑不在 |
| `rejected{code}` | 终止状态 |
| `closed` | 调用了 `close()` |

- **同一进程只有一个会话**：同一个进程里，对同一台电脑（按 server、host、device 区分）只建一个会话，UI isolate 和后台服务 isolate 共用它。这样就不会再出现两边用同一个 deviceId 互相顶号的情况。

### 中继的限额（沿用 v1 的环境变量）

- **限额默认值**：
  - 每个 socket 每秒最多 512 帧、8 MiB，超出就 `RATE_LIMITED` 并断开
  - 每个地址每小时最多发送 `DSBOT_LINK_MAX_MB_PER_HOUR`（512）MiB
  - 每个地址最多 `DSBOT_LINK_MAX_SOCKETS_PER_ADDRESS`（256）个 socket
  - 每个地址每小时最多注册 `DSBOT_LINK_MAX_NEW_DEVICES_PER_HOUR`（20）台新设备
  - 总共最多 `DSBOT_LINK_MAX_SOCKETS`（1024）个 socket、`DSBOT_LINK_MAX_LINKS`（1024）条链路
- **慢消费者**：一个 socket 的待发队列超过 4 MiB 时关闭它。它会重新 attach，由发送端重传。
- **其他设置**：
  - `DSBOT_LINK_DATA`：设备表文件
  - `DSBOT_LINK_TRUST_PROXY`：设为 `1` 时取 `X-Forwarded-For` 的最后一项作为客户端地址
  - `DSBOT_LINK_DEVICE_TTL_DAYS`：多少天没出现的设备会被忘掉
  - `DSBOT_LINK_GRACE_SECONDS`：宽限期
  - `HOST`、`PORT`：监听地址
- **其他行为**：`/healthz` 返回 `ok`。浏览器页面只能从中继自己的源连接；手机 App 不带 `Origin`，不受这条限制。

### 电脑端（ds-bot 插件）

- **产物**：`ds-bot/link.js` 由 `scripts/build-link.mjs` 打包生成，`ds-bot/link.wasm` 是 Rust 编译出的 wasm，两个都提交进仓库，都列在 `package.json` 的 `files` 里。
- **导出的名字**：沿用 `DeviceRegistry, HostLink, LINK_PATH, deviceIdFor, generateKeyPair, identityFingerprint, pairingUri, parsePairingUri, randomToken`，另外为测试加了 `PhoneLink`、`RelayCore`。`phone.json` 的格式不变。
- **旧地址迁移**：`phone.json` 里的 `server` 如果是默认中继的 `/v1/link`，自动改成 `/v2/link`。
- **`build-link.mjs --check`**：比对写在 `link.js` 文件头里的源码哈希。哈希覆盖所有会编进 wasm 的源码，包括 `link/crates` 下的 core、host、client、relay、wasm 和 `link/js`，以及 `link/Cargo.lock`；手机端运行时、中继服务端和测试不算在内。这样 `npm test` 不需要装 Rust。真正编译 wasm 放在 Rust 的 CI 任务里做。

## 不做什么

- 不和 v1 互通，也不在同一个中继进程里同时提供 v1。
- 不做直连和打洞，不做 QUIC。以后可以在可靠通道下面换一种传输。
- 中继不缓存数据帧，重传由两端负责。
- 不做 Noise 的 rekey。seq 是 u64，用不完。
- 不改应用层：`RemoteMessage` 的格式、`api/bot` 的端点和负载都不变。

## 已知限制

- Android 会冻结后台进程。冻结时间超过宽限期（默认 120 s），回来时会走一次新的握手和全量同步。想在后台长时间保持连接，需要打开前台服务。
- 手机端用 `webpki-roots`，不信任用户自己安装的 CA，所以自建中继必须使用公网可信的证书。
- 宽限期内，电脑为每条暂时离开的链路最多缓存 8 MiB。超出就关闭链路，手机回来后重新全量同步。
